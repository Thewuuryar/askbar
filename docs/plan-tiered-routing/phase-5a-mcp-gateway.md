# Phase 5A: MCP gateway (branch `feat/mcp-gateway`)

Previous: [Phase 4](phase-4-egress-proxy.md) · Next: [Phase 5B](phase-5b-research-judge.md) · Tracker: [task-tracker.md](../task-tracker.md)

Part of [the tiered routing plan](../plan-tiered-routing.md). Its How to run, Owner gates and Assumptions sections apply to every step here.

The MCP gateway is a purpose-built Rust service in this repo, the same call the owner made for the egress proxy (G13, decided 2026-11-24: no third-party gateway): component and compose service `mcp-gateway`, crate `services/mcp-gateway` (package `askbar-mcp-gateway`), API `/api/mcp-gateway/v1` ([ADR 0022](../adr/0022-api-path-conventions.md) pattern), uid 10007, the MCP gateway ADR (P5A.2). `search` and `fetch` are native in-process tools. Its API is REST with problem+json, so W3 has no MCP wire code. `rmcp` (the Rust MCP client) and a third-party MCP server come only at G16, as one more tool kind in the front's registry; agentgateway is the runner-up, to be added then as one upstream behind the same front.

Needs Phase 4 (the proxy and its P4.4 push), G0, and from P5A.2 the owner's acceptance of the MCP gateway ADR (ADR 0001 rule 3: a new service and image need one). Steps marked **[draft PR]** change `compose.yaml`, a Dockerfile, a network or a volume: the orchestrator opens the PR as a draft and waits for the CI `isolation` job (no Docker locally) before the owner marks it ready. **[owner]** marks an action only the owner can take: `.github/workflows/` is theirs, and P5A.12 and P5A.13 list the exact `ci.yml` and `images.yml` lines to add `mcp-gateway` and the `searxng` image to in the PR body. Values introduced here (approval expiry 60 s, fetch size, time and hop limits, the one-time ID window) go in `constants.rs`, with bounds in `askbar-proto` where a service checks them; the front gets them in config pushes (ADR 0028). Tool output is untrusted data everywhere. `search` and `fetch` are each a per-user permission, off by default.

## How it works (the plan's decisions; the MCP gateway ADR records them in P5A.2)

- **Front and tools.** `mcp-gateway` is built on `askbar-service` (boot, token links, `AuditClient`, status, not-configured gate). Its tool registry maps a tool name to a native handler (`search`, `fetch`). The ADR records that the registry will gain a second kind, upstream-MCP (`rmcp`, G16); no client API changes then. Not built now.
- **Who calls whom.** `server` calls the front (`server-mcp-gateway`) with the tool, the exact arguments and the approval that `model-gateway` signed. The admin pushes config (`admin-mcp-gateway`). The front writes `tool` spans through `mcp-gateway-auditor` (audit span kind `tool`, per the cross-track decisions in [plan-priorities.md](../plan-priorities.md)). It has no route to `/api/server/v1`, the admin API or `model-gateway`.
- **Networks (all `internal` but the proxy's).** `mcp-server`, `mcp-admin`, `audit-mcp-gateway`, `mcp-searxng` (front and `searxng` only), `egress-searxng` (`searxng` and the proxy), `egress-fetch` (front and the proxy). Nothing else joins them.
- **Approval.** Ed25519 with `ring` (already in `Cargo.lock`; no new crate; the licence is on the `deny.toml` allowlist because `cargo deny` passes today). `Approval` and `ToolAction` live in `askbar-proto` with no crypto (it is built into the desktop client). Key generation, sign and verify live in `askbar-service` behind a new optional `approval` feature, as `backup` is for `age`; `admin`, `model-gateway` and `mcp-gateway` turn it on. The action hash is SHA-256 over canonical JSON (sorted keys, no floats; `sha2` is already a dependency). Verify checks signature, hash, 60 s expiry and a one-time ID; the front keeps seen IDs in memory for the window. A separate crate only if the Phase 9 executor must verify outside `askbar-service`.
- **Check order on a call.** Config present (else fail closed) → approval → tool permission → open the audit span and wait for the auditor's acknowledgement → run the tool → close the span with the outcome. A failure at any step refuses with problem+json and a distinct code before anything is run.
- **`search`.** The front posts the query to `searxng` over `mcp-searxng` and returns at most N results (title, URL, snippet; N from `constants.rs`) marked untrusted. It remembers each task's result URLs (bounded) for the fetch rule.
- **`fetch` (G15).** The signed `ToolAction` carries the URL, its provenance (`search` or `user`) and a `query_data` flag (additive fields). The front refuses: a `search` URL not among this task's remembered results; any URL with a query string unless `query_data` is signed; a scheme but http and https; a port but 80 and 443; userinfo; a non-ASCII host; an IP literal (same host check as the proxy, from `askbar-proto`). It sends the request through the proxy's `fetch` listener (`CONNECT` for both schemes, hostname unresolved, so the proxy resolves and connects in one step and is authoritative for private-range blocking), follows redirects itself (hop cap in `constants.rs`, each hop re-checked and given its own `tool` span before it is requested, https to http refused), sends `Accept-Encoding: identity` and refuses any `Content-Encoding` (so the size cap counts real bytes and no decompression crate is needed), stops at the size cap and the total time cap, accepts only `text/html`, `text/plain` and `application/xhtml+xml` without sniffing, sends no cookies, no credentials and no `Referer`, and a fixed honest `User-Agent`. HTML becomes text by a small hand-written pass (drop `script` and `style`, strip tags, decode the common entities); no JavaScript runs. The text is returned with `untrusted: true`, with control characters and the datamark character removed so a page cannot forge a marker. The datamarking itself happens where the writer prompt is built (W5.3, track 1 decision).
- **Egress sources (the plan change to Phase 4).** The proxy gets two sources: `searxng` (`egress-searxng`; exact engine hosts) and `fetch` (`egress-fetch`; one `any_public` entry for ports 80 and 443, added to Phase 4's P4.1a, with ADR 0056 amended in P5A.30). `fetch` has its own source because a wildcard-public fetch is an exfiltration channel: it must not share an identity with a later credentialed server, which gets its own source and exact hosts at G16.
- **`searxng` container (G9b, G14).** The unmodified upstream image (AGPL-3.0 as a separate unmodified container, with a source link in `scripts/third-party-notices.images.md`; this is the author's reading, not legal advice), pinned by digest, in a derived image that adds only the settings file and a start script writing a random `secret_key` into tmpfs (no secret in an environment variable, no committed secret; nothing uses sessions with the limiter off, so an ephemeral key is fine). Hardened per ADR 0032: non-root (the upstream image has no `USER`; P5A.13 spikes it), read-only root, `cap_drop: ALL`, `no-new-privileges`, tmpfs, memory limit. Settings: metrics, autocomplete, image proxy and limiter off; `json` the only output format; `safe_search` 2; only the `tracker_url_remover` plugin; engines duckduckgo, brave, mojeek and wikipedia, no Google or Bing; `outgoing.proxies` is the proxy's `searxng` listener.
- **Config and admin.** The admin pushes the registry of built-in tools, per-user permissions, the constants and the approval public key to `PUT /config` (ADR 0028); before the first push the front refuses every call.
- **Zero new crates.** `ring` (promoted from a transitive dependency to an optional direct one of `askbar-service`), and the workspace's own. `reqwest` as `model-gateway` has it. Anything else is an owner note below.

## G16 checklist for each further MCP server

This is the policy text for approving each further MCP server (G16, decided 2026-11-24). A server needs every point answered in the PR that adds it.

1. **Need:** which user task needs it, and why `search` and `fetch` do not cover it.
2. **Provenance:** upstream repository, licence on the `deny.toml` or image allowlist, maintainer, last release (under 6 months), pinned version or digest; a new image takes the ADR 0026 steps.
3. **Transport:** how it runs (remote HTTPS, or a static stdio binary); no shell tool, no file-system tool, no code execution (AGENTS.md: the model gets none through 1.0).
4. **Tools:** each tool and its argument schema, marked read-only or side-effecting; side effects need a signed approval and the judge.
5. **Credentials:** minimal scope, held in memory, pushed by the admin, never in an environment variable, log or `/status`; a rotation path.
6. **Egress:** exact hostnames and ports, one allowlist entry per destination, its own proxy source; no wildcard; no private address unless the owner approves that host.
7. **Data:** what leaves the house and what comes back; output is untrusted; a `tool` span for every call; payloads sealed.
8. **Permissions:** off by default for every user; per user and per tool; deny wins.
9. **Tests:** unsigned, replayed, swapped, expired, audit-down, permission-off, oversize and timeout are all refused (the P5A.20 to P5A.22 pattern).
10. **Exit:** how to disable and remove it; removal drops its credentials and egress entries.

## Decisions and open owner notes

- **No third-party gateway (G13).** Search and fetch need none of federation, stdio or OAuth, and every check that matters is in the front in either case. Revisit at G16 only if the server list outgrows a small `rmcp` client; then agentgateway is a later upstream behind the front, after its own spike (arguments in its rules, a proxy tunnel for backend traffic, JWT algorithms, memory, the UI port, non-root are all unverified).
- **`ring` for Ed25519 (G9a).** No new crate. Note for the owner: `ring` 0.17.14 is the newest release and is 20 months old as of the research; low risk for a stable primitive. Fallback `ed25519-dalek` 3.0 is a new crate: **Owner decides** if `ring` is refused.
- **Approval code in `askbar-service` (G9c).** Types in `askbar-proto`, no crypto there. A separate crate only if the Phase 9 executor needs it.
- **`searxng` is the one third-party image,** unmodified upstream, pinned by digest, in a derived image that only adds settings and a start script. The AGPL-3.0 reading (a separate unmodified container) is the author's, not legal advice; **Owner decides** if counsel should check it.
- **Plan change to Phase 4.** The proxy gets an `any_public` entry (P4.1a) and two sources, `searxng` and `fetch`, wired here. The owner asked for the engine hosts to come from a log-only run; Phase 4 has no log-only mode, so P5A.13 uses the deny-and-read trial of P4.3b.
- **Fetch has its own source** because wildcard-public egress is an exfiltration channel; the signed URL, the query-data rule and the span before each hop are the defence. If credentialed servers arrive (G16), consider a separate container for fetch too.
- **Proxy authoritative, front advisory.** The front checks URLs for clear errors and sends the hostname in `CONNECT`; only the proxy's resolve-and-connect closes DNS rebinding.
- **No decompression.** `Accept-Encoding: identity` and refusing any `Content-Encoding` keeps the size cap honest with zero new crates; a few sites may then refuse. **Owner decides** if a decompression crate is wanted later.
- **HTML to text is hand-written** (no HTML crate is in `Cargo.lock`). It is a stated shortcut: upgrade to a crate (an owner decision, new dependency) if extraction quality is poor.
- **robots.txt: Owner decides.** The plan does not read it for user-initiated fetches.
- **Datamarking** is applied where the writer prompt is built (W5.3); the front only marks output untrusted and strips the marker character.
- **The G16 checklist above is the policy** for each further server; P5A.16 waits for the first approval.
