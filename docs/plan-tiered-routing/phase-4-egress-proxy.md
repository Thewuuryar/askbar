# Phase 4: egress proxy (branch `feat/egress-proxy`)

Part of [the tiered routing plan](../plan-tiered-routing.md). Its How to run, Owner gates and Assumptions sections apply to every step here.

The egress proxy is a purpose-built Rust service in this repo (G8, decided by the owner): component and compose service `egress-proxy`, crate `services/egress-proxy` (package `askbar-egress-proxy`), API `/api/egress-proxy/v1` ([ADR 0022](../adr/0022-api-path-conventions.md) pattern), uid 10006, new ADR 0056. It is the only service with a route out, except Caddy (certificates). It never sees content: HTTPS passes as a `CONNECT` tunnel, with no TLS interception.

Needs G8, G0 (cleared: `constants.rs` is on `main`) and, from P4.1a, the owner's acceptance of ADR 0056. The steps are in run order, which is not numeric order: P4.4, P4.4a and P4.4b run before P4.3a, because the proxy denies everything until the admin pushes, so a caller moved before the push would lose its route. Each step's commit passes the checks on its own.

Steps marked **[draft PR]** change `compose.yaml`, a Dockerfile, a network or a volume. The orchestrator opens the PR as a draft and waits for the CI `isolation` job (there is no Docker locally) before the owner marks it ready. `.github/workflows/` is the owner's: P4.2 lists the exact lines to add `egress-proxy` to (`ci.yml` build and image loops, `images.yml` `SERVICES` and its two image lists) in the PR body.

## How the proxy works (the plan's decisions; ADR 0056 records them in P4.1)

- **Source = the network it arrives on.** One internal network per source (`egress-model-gateway`, `egress-cpa`, `egress-alerter`), the proxy attached to each, a listener per source bound to the proxy's address on that network (never a wildcard) from `ASKBAR_EGRESS_PROXY_SOURCES=model-gateway=egress-model-gateway-host:3128,...`. Why: no secret in a URL or variable (AGENTS.md), nothing to steal or forge, and a compromised source cannot claim another's allowlist because it is on no other source's network. Better than source-IP matching (Docker assigns addresses). A new source (searxng, `mcp-gateway`) is one network, one alias and one entry in that variable.
- **Default deny.** Before the first push the proxy has an empty config and answers every request `403`. A `PUT /config` replaces the whole config in memory; nothing is on disk.
- **Allowlist entry** `{host, port (default 443), plain_http (default false), allow_private (default false), relay (default false)}` per source. A source name the proxy has no listener for is refused (`400`).
- **Host check.** ASCII only (an IDN is entered as `xn--` punycode; non-ASCII is refused: no IDNA tables, no new crate). Lower-case, one trailing dot stripped, no userinfo, port parsed apart, label and length rules. Any host whose last label is all digits or starts `0x`, and any decimal, octal, hex or short IPv4 form, is an IP literal and refused unless it is the canonical dotted quad or bracketed IPv6 that an entry names exactly. Compared as whole names, never suffixes or wildcards.
- **Address check, rebinding defence.** The proxy resolves with `tokio::net::lookup_host` once per connection, classifies every returned address, refuses the connection if any is non-public (loopback, RFC 1918, 100.64/10, link-local incl. 169.254.169.254, unspecified, multicast, broadcast, documentation and benchmark ranges, IPv6 ULA, link-local, site-local, IPv4-mapped and NAT64 forms judged by the embedded IPv4) unless the entry has `allow_private`, then connects to the validated `SocketAddr` itself and never to the name again. Same for plain HTTP and the relay.
- **Plain HTTP** is needed today (a LAN ntfy server, the dev mock LLM, a self-hosted decider), so it is supported but only for an entry with `plain_http`: absolute-form requests are rewritten to origin-form with `Connection: close` and relayed once.
- **Relay.** SMTP is not HTTP and `lettre` cannot use a proxy. The alerter's mail used to leave directly over `alerter-outbound`; the owner chose the relay, so it goes through the proxy like the rest. The proxy gives a source with a `relay` entry one extra fixed port (`ASKBAR_EGRESS_PROXY_RELAYS=alerter=egress-alerter-host:2525`) that tunnels to that entry's host and port under the same checks. The alerter connects `lettre` to the relay address and keeps the real host as the TLS name (`TlsParameters::new`), so STARTTLS and certificate checks are unchanged.
- **Limits** (defaults in `askbar-proto`, pushable, with bounds): request head 8 KiB, header lines 64, connect 10 s, head read 10 s, tunnel idle 120 s, 256 tunnels in all and 128 per source.
- **Logs and status.** `tracing` fields `source`, `host` (at most 253 ASCII bytes, as validated; an invalid name is logged as `invalid`), `verdict` and a reason code. No URL, path, port, header or byte count of content. `GET /status` has `configured`, `version`, `boot_id`, open tunnels, per source the counts allowed and denied by reason, and `recent_denied`: the 50 most recent denied attempts, newest first, in memory only (`source`, `host` as validated or `invalid`, `port`, `reason`, `at`). No path or content. The admin shows this list (P4.4b); the proxy raises no alert.
- **Config link.** `admin-egress-proxy` (token prefix `admegr_`), network `egress-admin`, admin to proxy only. The proxy calls nobody: no link to the auditor or the alerter.
- **`cpa` allowlist.** Only Anthropic and OpenAI hosts, the providers behind the two subscription logins; nothing else for `cpa` (P4.3b).
- **Zero new crates.** `tokio`, `axum` 0.8 (API only), `serde`, `tracing`, `askbar-proto` and `askbar-service`. The request head is parsed by hand.

## Decisions and open owner notes

- **Source identity** is the network and its listener, not a credential: no secret in an environment variable or URL (AGENTS.md); a better scheme would need a secret or fixed addresses.
- **No TLS interception, CONNECT only for HTTPS;** the proxy cannot see or alter content.
- **ASCII hosts only** (punycode entered as `xn--`): no IDNA tables, so zero new crates and no normalisation mismatch to exploit.
- **Any non-public address among the answers refuses the connection,** and the connect uses the validated address: one resolution per connection closes rebinding.
- **Plain HTTP is supported only per entry** (`plain_http`), because a LAN ntfy, the dev mock and a self-hosted decider need it today.
- **SMTP goes through a per-source relay port,** not `CONNECT`, because `lettre` has no proxy support; the TLS name stays the real host. Decided by the owner: the relay, not an open network for the alerter's mail, so no ADR 0006 exception.
- **Allowlists are derived by the admin** from provider URLs, the alert settings and a fixed `cpa` list; private addresses are allowed only by an audited admin approval (P4.4a).
- **Blocked attempts raise no alert (owner decision).** They are logged (source, host, verdict, reason; never a path or content) and the admin shows the proxy's 50 most recent in the Services page (P4.4b) from its existing `/status` poll. The proxy has no link to the alerter or the auditor. Owner decides later: keeping the list across a proxy restart needs the auditor link; not built now.
- **`cpa` is limited to Anthropic and OpenAI hosts for now (owner decision),** the providers behind the two subscription logins. P4.3b's trial finds the exact host names and keeps only those that belong to the two vendors.
- **The alerter goes through the proxy (owner decision):** ntfy by `CONNECT`, mail by the relay port; no open network for mail, no ADR 0006 exception.
- **Owner decides:** what happens if CLIProxyAPI cannot use a proxy (P4.3b options).
- **Limits** are pushed defaults in `askbar-proto`, constants in `constants.rs`; the numbers above are proposals for the owner to confirm in the PR.
- **Step order differs from numbers** (P4.4 and P4.4a before P4.3a): the proxy denies until pushed.
- **New crates: none.** ADR 0056 is new, and proposed; per `orchestration.md` the orchestrator never accepts it. `plan-refactor.md` and `plan-priorities.md` said P4.4 adds the link: it is P4.1c, and both are updated. R2 (P4.2) and P5A.19 (P4.4) stay true.
