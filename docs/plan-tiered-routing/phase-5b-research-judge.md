Runs in track 1 as stage W7 of [plan-priorities.md](../plan-priorities.md). Needs Phase 5A (done: signing, the MCP front, `search` and `fetch`), W4 (role pins) and W5 (quick search, the pattern copied here). No step here changes `compose.yaml`, a Dockerfile, a network or a volume, so none is a draft PR. Values introduced here (tool-call limit, token cap, researchers, waits, summary size, one running task per user) go in `constants.rs` with bounds in `askbar-proto`, pushed to `model-gateway` and the server as the quick search limits are (W5.1, P8.6d). ## How it works (the owner's decisions of 2026-11-25; the amendments in P5.17 and P5.18 record them)

- **Start.** The client chat request gains `research: bool`, as `web_search` is (additive, left out when off; research wins if both are set). `Settings` gains `research: bool`, true when the user holds both the `search` and `fetch` tools and the three research roles are pinned, so the client shows its toggle (P5B.6). The report is the reply, with its sources (the existing `sources` event). Client task views stay in Phase 6.
- **One task is one reply.** The task id is the reply's generation id, so every span and model call of the report is one trace and the quick search route's task-id rule holds. `tasks.kind = 'research'`; Phase 6 adds other kinds to the same tables.
- **Flow, linear, no loop.** All of it runs in the server; the server calls `model-gateway` for model calls and approvals and the MCP front for tools.
  1. Fail early with a plain note when a role is unpinned (`role_not_pinned`), a tool is missing, or the user already has a running research task (`research_busy`, 409).
  2. **Split** (`research.writer`, sees only the message): 2 to 4 sub-questions, 1 if short.
  3. **Research**, one researcher per sub-question, in parallel. Each is allotted `tool_calls / n` calls (the gateway is the authority on the shared total). A researcher makes one model call (`research.researcher`, sees only its sub-question) that proposes one query, then the search, then fetches of result URLs from that result only, then one model call that summarises the datamarked pages in at most 800 tokens. Queries are fixed before any page is read and fetches come only from results, so nothing a page says can cause another call. A result URL with query data is listed as unfetched, never fetched (as quick search does).
  4. **Wait:** after 2 summaries wait 8 s for the rest; the stage stops at 90 s. 0 summaries: the request fails with a plain note. 1: the report is marked single-source (this includes a question that was not split).
  5. **Write** (`research.writer`): "Source 1, Source 2..." summaries only (never page text); notes agreement, conflicts and gaps; drafts the cited report. The server builds the source list from its own fetch results, so a page cannot add a source.
  6. **Judge** (`judge.review`, `POST /decide`): sees the question, the summaries and the draft, never raw page text. It answers approve, or refuse with a reason code, in a fixed format. A refusal ends the report with a plain note instead of the draft.
  7. **Deliver** the report only after the judge approves.
- **No per-call judge.** Every search and fetch is approved by fixed rules, as in quick search, because nothing a page says can cause another call. The judge reviews the draft instead. This replaces the design's "each tool call through the judge" and "the writer streams" ([design](../design-tiered-routing.md#research-reports), [judge](../design-tiered-routing.md#judge-and-tool-approvals); not edited, see the notes below). A report is therefore not streamed token by token: the judge must approve the whole draft before the user sees any of it, so the server sends additive `progress` events while it works (`splitting`, `researching` with done and total, `writing`, `reviewing`), then the report text in one `delta` and the `sources` event.
- **Who calls whom, and the audit spans.** `model-gateway` writes the `turn` and `step` spans of every model call with the `role` attribute (W5.3's rule), including the judge's call, whose span records the verdict and reason code and no text. The MCP front writes the `tool` spans (P5A.9). The server opens only `gate` spans (for refusals). The gateway opens a `gate` span for each approval before returning it. Sealed payloads: prompts and replies as in W5.3; summaries and the draft only in the judge's and writer's request payloads.
- **Approval route: a new `POST /approvals/research`**, not an extension of the quick search route. Quick search counts per reply (queries, pages, searches per hour); research counts per task (one tool-call total shared by all researchers, no hourly rule). One function with both rule sets would be harder to read than a second small one that shares `approve`, `shape` and `gate_blocked`. It never calls a model. Request: `ResearchApprovalRequest {task_id, user, tool, arguments}`. It refuses: research switched off (`research_disabled`), tool not `search` or `fetch`, bad arguments, the task's tool-call limit reached (`task_tool_calls`), user paused, kill switch. Each refusal has its own `ErrorCode`.
- **The judge's fixed input and output.** `POST /decide` with `decision: judge` takes `{task_id, user_id, question, summaries: [{source, urls, text}], draft}` (typed in `askbar-proto`; `step_check` and `research` are refused until P5.8). The gateway builds the prompt from a fixed template, with the summaries and the draft between markers as data. The model must answer exactly `{"verdict":"approve"}` or `{"verdict":"refuse","reason":"<code>"}`, `reason` one of `unsupported_claim`, `contradicts_source`, `off_topic`, `unsafe`, `bad_citation`. Anything else (extra fields, extra text, a reason outside the list) is a refusal with reason `bad_format`. It fails closed: judge unpinned (`role_not_pinned`), unavailable, over the cap (402) or malformed all end as a refusal in the server. No approval is signed: there is no tool call to approve.
- **Task tables (P5.9).** In the space's SQLite file, appended as a migration, deleted with the conversation, backed up with the file: `tasks` (id, conversation, `kind`, user, status `running|done|stopped|interrupted`, tool calls used, tokens used, cap, times) and `task_steps` (task, step number, role, status, outcome, output). A step row is written before it starts and updated at its end; step outputs are the summaries and the draft (untrusted). On start the server marks `running` tasks `interrupted`; the interrupted reply already shows its plain note through the existing interrupted-generation path; there is no resume and no cancel in W7 (P6.15).
- **Token cap accounting.** A task's calls are the ones with a task role (`research.researcher`, `research.writer`, `judge.review`), keyed by the generation id. `model-gateway` keeps an in-memory counter per task id, bounded like `QuickCounts`, adds the provider's usage after each call, and before each model call refuses with a 402 `problem+json` (`task_token_cap`) when the counter is at or over the cap. The same counter holds the tool-call count that `POST /approvals/research` reads. Usage also counts per role against the user's budget through the existing path (W4.2), so the budget still applies as well. Shortcut: the cap is checked before a call, so one call can pass it by its own size, and a gateway restart zeroes the counters (the task is cut by the restart anyway); the server's `tasks.tokens_used` is the durable figure for display.
- **Alerts at 75% and 90% (P5B.4).** The gateway cannot reach the alerter and the auditor sends fixed kinds of its own. The smallest path: the gateway's `GET /status` gains two counters (tasks that crossed 75% and 90% of their cap); the admin already polls that status, and turns an increase into a new alert kind `task_cap_threshold` (a sender of the admin, field `percent`) through the alerter it already has. The user sees the same crossing as a `progress` note in the stream.
- **Roles and the admin.** `Role` gains `research.researcher`, `research.writer` and `judge.review`; the W4.2 Roles section lists them (its role list is fixed in `services/admin/src/roles.rs`) and usage per role covers them. The new limits join the Search page's limits table under a "Research" group (the P8.6d editor, endpoint and push), not a new page. No default pins: an unpinned research role or judge is refused and the user reads "Research is not set up."

## Decisions and open owner notes

- **Owner decisions, 2026-11-25 (binding).**
  1. Research starts with a `research` boolean on the chat request, like `web_search`, and a client toggle (like W5.4); the report is the reply with its sources; client task views stay in Phase 6.
  2. Information is gathered as quick search does: fixed-rule approvals signed by `model-gateway`, linear, no per-call judge. The judge reviews the draft: researchers summarise (summaries only, 800 tokens each), the writer drafts from the summaries, the judge checks the draft against the summaries and the question and answers approve or refuse with a reason code in a fixed format; it fails closed; a refusal ends the report with a plain note; the judge never sees raw page text; the report is delivered only after approval.
  3. Task token cap default 300,000 per task across researchers, writer, judge and the query and split calls; range 20,000 to 2,000,000; over cap is a 402 `problem+json`; alerts at 75% and 90%; checked before each model call.
  4. A URL with query data is refused and listed as unfetched, as quick search does.
- **Deviation from the design, on purpose.** [The design](../design-tiered-routing.md) says the judge approves every research tool call and the writer streams the report. Neither holds in W7 (owner decision 2026-11-25): the judge reviews the draft, and the report is not streamed because it is delivered only after approval (progress events instead). The design file is not edited here; the P5.18 amendments record it. P5.6 therefore takes the draft review and not a per-tool-call approval.
- **Defaults the owner may change.** Tool-call limit 8 per task (1 to 32; searches plus fetches, shared across researchers); 2 to 4 researchers; after 2 summaries wait 8 s, stage stops at 90 s; 0 summaries fails, 1 is marked single-source; summary 800 tokens; one running research task per user; no cancel in W7; interrupted tasks show a plain note and do not resume; no default pins (an unpinned research role or judge refuses with "Research is not set up"); step outputs are stored in the space file and deleted with the conversation; task id equals the generation id; approvals by a new route, not the quick search one; alerts through a new `task_cap_threshold` kind polled by the admin from the gateway's status; the limits sit in the Search page's table.
- **Open questions the docs do not settle.** (a) Decided: W7 has no judge backup pin (W4 pins hold one model per role). An unpinned, unavailable or over-cap judge fails closed and the report ends with a plain note. The backup pin and the design's wish that the judge run on a different provider than the researchers are deferred to track 4; P5B.3 only hints at it. (b) The "single-source" marker also covers a question that was not split. (c) Decided: research has its own global switch `research_enabled` (P5B.3), on by default and independent of the kill switch and of quick search's switch. (d) The different-provider rule is deferred (see a). (e) ADR 0009 does not mention tasks yet (P0.12 is unticked): P5.17 carries the amendment when P0.12 has not landed.
- **Stays out of W7:** P5.7 (decider cascade), P5.8 (step checks, research filters), tiers, dollar budgets, cancel and resume (P6.15), client task views (P6.14, P6.20, P6.21), admin task views (P8.6b), a writer that calls tools, memory writes.
