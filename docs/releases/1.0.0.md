# Askbar 1.0.0

Askbar is a Spotlight-style AI popup. You press a hotkey, a bar appears, you type a question, read the answer and press Esc. Your own server holds the conversations and the provider keys, and the desktop app is a thin client that pairs with it. It is an open-source project for personal hardware (AGPL-3.0-or-later), with no support or uptime guarantee.

1.0.0 is the scope of [ADR 0002](../adr/0002-v1-scope-limits-and-ship-criteria.md): conversation only (text in, text out: no tools, no shell, no file access), on a server split into separated containers.

## What is in it

- A desktop popup for macOS, Windows and Linux, opened with a global hotkey, and an admin site at `/admin`.
- Any model provider: Anthropic, anything OpenAI-compatible, or a Claude or ChatGPT subscription through CLIProxyAPI.
- Replies run on the server and carry on if the window closes. History and search, in a personal space for each user.
- Users and pairing keys; HTTPS from the first start with the install's own certificate, then Let's Encrypt for your own host name.
- Separated, hardened containers: `server`, `admin`, `auditor`, `model-gateway`, `alerter`, `caddy` and `cpa`, with `bootstrap` creating the per-link tokens. Only Caddy publishes ports, and no service has the Docker socket ([architecture](../architecture.md)).
- An audit trail of every reply, with prompts and replies sealed by a passphrase only the owner knows; alerts by ntfy or email; encrypted backups, by hand or on a schedule, and a restore.

## Known limits

- **Size.** There is no fixed limit on users. The tested size is three active users, three simultaneous replies against the mock model, and about 200 ms of added latency at the 95th percentile before the first token (the provider excluded).
- **No guarantees.** No support and no uptime guarantee. A restart from the admin takes under a minute; the target for a restore on a clean host is under 30 minutes (a person times it: see the checklist below).
- **Not in 1.0.** Shared spaces for a family, memory and an iOS app (deferrable, [ADR 0002](../adr/0002-v1-scope-limits-and-ship-criteria.md)); projects, VPN access, arm64 images and renaming conversations ([the guide](../guide.md#not-built-yet)).
- **The desktop client** has no offline mode, and it cannot register a global hotkey on Wayland (bind a shortcut to the command `askbar` instead). The installers are not signed by Apple or Microsoft, so macOS and Windows show a first-open warning ([Verifying images and files](../guide.md#verifying-images-and-files)).
- **Alerts.** Nothing outside the host notices if the alerter itself is down ([ADR 0016](../adr/0016-risk-register.md)); the admin site shows a banner.

## Before this is a release: the checklist

These are done by a person, not by CI. Each box stays empty until the owner has done it, on the release candidate that is to become 1.0.0 ([Staging a release](../guide.md#staging-a-release)). A fix gets its own pull request and a new candidate.

- [ ] A fresh deployment and one paired client work end to end, tested by a person.
- [ ] A real certificate is issued through this layout.
- [ ] A person completes a restore drill from a backup and meets the recovery target (under 30 minutes on a clean host).
- [ ] A person tests the client on macOS, Windows and Linux. On macOS and Linux, whose webviews are not Chromium, this includes that the popup's replies still render under its Trusted Types policy, that a link asks first and shows its whole address, and that the webview's console shows no content security policy error ([ADR 0044](../adr/0044-desktop-client.md)).
- [ ] The owner has signed off on the accepted risks ([ADR 0016](../adr/0016-risk-register.md)).
- [ ] No known ship-blocking finding remains open (the triage rule is in [ADR 0002](../adr/0002-v1-scope-limits-and-ship-criteria.md)).

The GitHub settings the release depends on are listed under [GitHub settings](#github-settings) at the end.

CI covers the rest of the ship checklist on every change: `scripts/check-isolation.sh` (including the failure drills), a test for every Defend row of the risk register, and the documentation checks.

## GitHub settings

The owner sets these once in the GitHub web UI; the agent never changes repository settings. Tick each box when it is done. A: Actions; B: the `staging` and `production` environments; C: the ruleset for `main`; D: the ruleset for release tags; E: the packages (needs the first `images.yml` run on `main`); F: security features; G: your own notifications; H: CodeQL (needs `.github/workflows/codeql.yml` on `main`).

### A. Actions permissions

In the repo: **Settings → Actions → General**.

- [ ] **Actions permissions:** *Allow all actions and reusable workflows*. Every action is already pinned by commit hash. For a tighter setting, choose *Allow Thewuuryar, and select non-Thewuuryar, actions* and list `actions/*`, `docker/*`, `dtolnay/*`, `Swatinem/*`, `EmbarkStudios/*`, `aquasecurity/*` and `sigstore/*`.
- [ ] **Approval for fork pull request workflows:** *Require approval for all external contributors*.
- [ ] **Workflow permissions:** *Read repository contents and packages permissions*. Each workflow asks for more in its own `permissions:` block.
- [ ] **Allow GitHub Actions to create and approve pull requests:** leave it unticked.
- [ ] Save.

### B. Environments

**Settings → Environments → New environment.**

- [ ] **Name: `staging`** → *Configure environment*.
   - **Deployment protection rules:** none. No reviewer, no wait timer.
   - **Deployment branches and tags:** choose *Selected branches and tags* → *Add deployment branch or tag rule*.
     - **Ref type:** Tag.
     - **Name pattern:** `v*-rc*`.
     - *Add rule*.
   - **Environment secrets and variables:** none. Publishing uses the workflow's own `GITHUB_TOKEN`, and signing uses OIDC, so nothing is stored.
- [ ] **New environment, name: `production`** → *Configure environment*.
   - **Required reviewers:** tick it and add yourself.
   - **Prevent self-review:** leave it unticked, or you could never approve your own release.
   - **Wait timer:** 0. You may set it to a few minutes, to leave a window for cancelling.
   - **Allow administrators to bypass configured protection rules:** untick it, so every production push waits for your click.
   - **Deployment branches and tags:** *Selected branches and tags* → *Add deployment branch or tag rule*.
     - **Ref type:** Tag.
     - **Name pattern:** `v*.*.*`.
     - *Add rule*.

     GitHub's patterns can't exclude an rc tag. The workflow sends `-rc` tags to `staging` itself, and step D means only you can create tags.
- [ ] **Save protection rules.**

A tag push then shows *Waiting* under **Actions**. Open the run → *Review deployments* → tick `production` → *Approve and deploy*.

### C. Ruleset for `main`

**Settings → Rules → Rulesets → New ruleset → New branch ruleset.**

- [ ] **Ruleset name:** `main`. **Enforcement status:** Active.
- [ ] **Bypass list:** leave it empty. An emergency fix still goes through a pull request (ADR 0001 rule 5 lets its ADR follow later).
- [ ] **Target branches:** *Add target* → *Include default branch*.
- [ ] **Rules:**
   - **Restrict deletions:** on.
   - **Require linear history:** on. Merges are squash or rebase only (AGENTS.md).
   - **Require a pull request before merging:** on.
     - **Required approvals:** 0. You can't approve your own pull request, and your merge is the approval.
     - **Require conversation resolution before merging:** on.
     - **Allowed merge methods:** Squash and Rebase.
   - **Require status checks to pass:** on.
     - **Require branches to be up to date before merging:** on.
     - *Add checks*: `lint`, `test-services`, `test-desktop`, `isolation`, `dependencies`, `images`, `cpa-image` and `secrets`. A check appears in the picker only after it has run once on a pull request; all of these already have. Pick the ones from the GitHub Actions source.
   - **Block force pushes:** on.
- [ ] **Create.**

### D. Ruleset for release tags

**Rulesets → New ruleset → New tag ruleset.**

- [ ] **Name:** `release tags`. **Enforcement:** Active.
- [ ] **Bypass list:** *Add bypass* → *Repository admin* → mode *Always*. That is you. Nothing else is listed, so neither an agent nor the Claude GitHub App can create, move or delete a release tag.
- [ ] **Target tags:** *Add target* → *Include by pattern* → `v*`.
- [ ] **Rules:** *Restrict creations*, *Restrict updates*, *Restrict deletions* and *Block force pushes*, all on.
- [ ] **Create.**

### E. Packages

After `images.yml`'s first run on `main` has pushed the edge images. The images stay **private for now**.

- [ ] Go to `https://github.com/Thewuuryar?tab=packages`. There is one package for each image: `askbar-bootstrap`, `-server`, `-admin`, `-auditor`, `-model-gateway`, `-alerter`, `-caddy` and `-cpa`.
- [ ] For each one: open it → **Package settings**.
   - **Manage Actions access:** `Thewuuryar/askbar` is listed with the *Write* role. It is added for you when the repo's workflow creates the package; if it is missing, *Add Repository*.
   - **Inherit access from source repository:** on.
- [ ] Check that a pull works once signed in (a GitHub token with `read:packages`):

   ```sh
   docker login ghcr.io -u <your-github-user>
   docker pull ghcr.io/thewuuryar/askbar-server:main
   ```

- [ ] **Later, only if you decide to make the images public:** for each package, **Danger Zone → Change visibility → Public** (type the package name to confirm). A public package can't be made private again, so do this only once you've checked the first images. Then check that a pull works without signing in, and delete the `docker login` lines from this page and the upgrade steps in these notes:

   ```sh
   docker logout ghcr.io && docker pull ghcr.io/thewuuryar/askbar-server:main
   ```

### F. Security

**Settings → Security** (the page may be named *Code security* or *Advanced Security*). Turn on:

- **Dependabot alerts** and **Dependabot security updates**. `dependabot.yml` expects both.
- **Secret scanning** and **Push protection**. Both are free for public repositories.
- **Private vulnerability reporting**, so reports can follow `SECURITY.md` without a public issue.

### G. Notifications for the CVE alert (D30)

This is your account, not the repo.

Go to **github.com/settings/notifications → System → Actions**.

- Tick **Email**.
- Tick **Only notify for failed workflows**.

The weekly scheduled `ci` run then emails you when a new advisory makes it fail. It is the CVE alert; there is no other. GitHub stops scheduled runs in a repository with no activity for 60 days, so push something now and then.

### H. CodeQL

After `.github/workflows/codeql.yml` is on `main`. It replaces GitHub's *default setup* for code scanning, because the default setup cannot analyse Rust only on pushes: a pull request analyses JavaScript, Python and the workflows (about one minute), and a push to `main` and the weekly run add Rust (about seven minutes). While the default setup is on, GitHub refuses the workflow's results, so switch:

- [ ] **Settings → Security → Code security** (or *Advanced Security*) → **CodeQL analysis** → the **⋯** menu → **Switch to advanced**. Confirm.
- [ ] Check that the next pull request shows `Analyze (javascript-typescript)`, `(python)` and `(actions)` from the `codeql` workflow, and that the next push to `main` also shows `Analyze (rust)`.

Alerts that are open stay open: both setups use the same result category for each language (`/language:<language>`). A pull request no longer shows new Rust alerts before merge; they appear on `main` after it.
